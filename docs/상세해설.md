## 01. 과제 목표: 변경을 설명하는 초안 만들기

**중심 질문:** 코드가 바뀌었다는 사실을 협업자가 이해할 문장으로 어떻게 옮기는가?

공통 예제는 사용자 저장소와 분리한 임시 저장소의 `calculator.py`이다. 기준 커밋에는 나눗셈만 있고, 이후 다음 두 줄을 unstaged 변경으로 추가했다. 이 변경을 01~10장에서 계속 사용한다.

```python
def divide(a, b):
    if b == 0:
        raise ValueError("0으로 나눌 수 없습니다.")
    return a / b
```

실제 API의 커밋 제목은 `divide 함수에 0으로 나누기 예외 처리 추가`였다. PR도 같은 변경을 Why·What·How to Test로 나누었다. 이 문장은 실제 생성 결과이고 예제 코드의 동작을 검증하는 테스트 결과는 아니다. Python의 기존 0 나누기도 예외를 발생시킨다. 이번 변경의 구체적 차이는 `ZeroDivisionError` 대신 명시적인 메시지의 `ValueError`를 발생시키는 것이다. 이를 단순히 “오류가 사라졌다”라고 설명하면 부정확하다.

과제의 다섯 학습 목표는 REST 요청·응답과 예외 처리, 생성 파라미터의 영향, Git 결과의 프로그램 입력 연결, 변경 맥락을 넣는 프롬프트, 결과의 검증·다듬기이다. 화면에는 이 흐름을 짧게 놓고 원고에서 서로 연결한다.

### 설명 원고 · 2분

“커밋 메시지는 저장할 변경을 짧게 설명하고, PR 설명은 다른 사람이 변경 이유와 내용, 확인 방법을 검토하도록 돕습니다. 오늘은 나눗셈 함수에 두 줄을 추가한 하나의 변경을 따라가겠습니다. 도구는 Git diff에서 변경을 읽어 AI에 전달하고, Python 검증기로 형식을 확인한 초안을 터미널에 보여줍니다. 실제 적용은 사용자가 결정합니다.

코드에서 `b`가 0이면 어떤 일이 일어날지 예상해 보세요. 기존에도 ZeroDivisionError가 발생했지만, 변경 후에는 명시적인 메시지의 ValueError가 발생합니다. 따라서 ‘오류가 사라졌다’라고 요약하면 부정확합니다. 생성 제목이 이런 동작 차이를 제대로 설명하는지 살펴봐야 합니다.

API 호출, 파라미터, 프롬프트, Git 연동, 결과 검증을 이 사례로 연결하겠습니다. 어떤 변경을 읽고 무엇을 외부로 보내는지, 어떤 형식을 허용하고 실패하면 어디서 멈추는지 확인합니다. 형식이 맞는 문장이라도 변경의 의미와 테스트 실행 여부는 마지막에 사람이 검토해야 합니다.”

## 03. 명령에서 처리 함수까지

명령은 `status`, `diff`, `commit`, `pr` 네 개다. 설치된 진입점 `output-6-1`은 `output_6_1.main:main`을 실행한다. `argparse`가 옵션을 해석하고 `set_defaults(handler=...)`로 등록한 함수를 호출한다.

```python
args = build_parser().parse_args()
try:
    args.handler(args)
except (OSError, RuntimeError, ValueError) as error:
    print(f"[ERROR] {error}", file=sys.stderr)
    raise SystemExit(1) from None
```

예: `output-6-1 commit --model gemini --temperature 0.2 --max-tokens 500 --safe-mode`.

`generate_commit()`은 상태 확인 → diff 확인 → `ai_commit()` → 출력 순서다. `generate_pr()`은 같은 흐름으로 `ai_pr()`를 부른다. `main.py`는 명령 처리, `git_service.py`는 subprocess와 UTF-8 해석, `ai_service.py`는 프롬프트·API·검증을 맡는다. 프롬프트와 후처리는 서로 다른 모듈 파일이 아니라 상수·함수 단위로 분리되어 있다.

“명령의 첫 단어는 할 일을, 뒤 옵션은 생성 설정을 정합니다. argparse가 입력을 Python 값으로 바꾸고 handler로 등록된 처리 함수를 실행합니다. 0.2는 실수, 500은 양의 정수로 해석됩니다. 명령 처리, Git 수집, AI 호출을 나눠 두었으므로 각 단계의 역할을 따로 확인할 수 있습니다.

## 04. Git에서 어떤 변경을 읽는가

**핵심 메시지:** 상태에 보이는 파일이 모두 생성 입력으로 들어가는 것은 아니다.

`git status --short`는 상태를 보여주고 `git diff`는 인덱스와 작업 파일의 차이를 보여준다. `git diff --cached`는 HEAD와 인덱스의 차이를 보지만 현재 생성 코드에서는 사용하지 않는다.

| 예제 상태 | status 결과 | 실제 생성 diff | 생성 명령 |
| --- | --- | --- | --- |
| 깨끗함 | 비어 있음 | 비어 있음 | 변경 없음 안내, API 0회, 종료 0 |
| unstaged 추적 파일 | ` M calculator.py` | 추가한 두 줄 포함 | 생성 가능 |
| staged만 존재 | `M  calculator.py` | 비어 있음 | 수집할 diff 없음, API 0회, 종료 0 |
| untracked만 존재 | `?? untracked.txt` | 비어 있음 | 수집할 diff 없음, API 0회, 종료 0 |

```python
def git_status() -> str:
    """변경 파일 상태를 간단한 형식으로 반환합니다."""
    return run_git(["status", "--short"])

def git_diff() -> str:
    """스테이징하지 않은 추적 파일의 변경 내용을 반환합니다."""
    return run_git(["diff"])
```

### 설명 원고 · 3분

“Git에는 작업 파일, 인덱스, HEAD라는 세 기준이 있습니다. 작업 파일은 편집 중인 내용, 인덱스는 다음 커밋에 넣으려고 고른 내용, HEAD는 현재 커밋을 가리킵니다. `git add`는 선택한 변경을 인덱스에 반영합니다. 현재 도구의 `git diff`는 작업 파일과 인덱스를 비교하므로 add한 변경만 있으면 생성할 diff가 비어 있습니다.

표의 ` M`은 작업 파일 쪽 수정이고 `M `은 인덱스 쪽 수정입니다. 새 파일은 `??`로 보이지만 기본 diff에는 내용이 없습니다. 따라서 status에 파일이 보여도 모두 모델 입력에 들어가는 것은 아닙니다. 한 파일에 staged와 unstaged가 섞이면 인덱스 이후 편집분만 들어갑니다. 프로그램도 ‘변경 없음’과 ‘git diff에서 수집할 변경 내용 없음’을 구분합니다.

계산기 변경을 add한 뒤 commit 생성 명령을 실행하면 무엇이 나올지 예상해 보세요. 이 명령은 Git 커밋 실행이 아니라 초안 생성입니다. PR도 base branch나 커밋 히스토리 대신 같은 현재 diff를 사용하므로 브랜치 전체 설명에는 맥락이 부족할 수 있습니다. staged 지원을 추가하려면 옵션과 혼합 상태의 의미를 함께 정의해야 합니다.

바이너리는 내용 대신 파일이 다르다는 안내만 들어갈 수 있습니다. 삭제·이름 변경·Git 설정도 diff 표현에 영향을 줍니다. UTF-8로 해석할 수 없는 출력은 수집 오류로 종료하므로, 이번 예제의 성공을 모든 저장소·인코딩에 대한 보장으로 넓히지는 않습니다.”

## 05. API에 보내는 정보의 범위

`--safe-mode`는 기본 OFF다. 켜면 `_prepare_diff()`가 원문 줄 수를 로그에 남기고 `limit_diff()`가 앞의 200줄을 고른다. 파일 수나 문자 수, 토큰 수를 제한하거나 비밀값을 마스킹하지 않는다.

```python
lines = diff.splitlines()
if len(lines) <= 200:
    return diff
return "\n".join(lines[:200]) + "\n\n[Diff truncated: limited to 200 lines.]"
```

| 원문 | 전송하는 원문 줄 | 안내문 추가 | 201번째 원문 줄 |
| --- | --- | --- | --- |
| 199줄 | 199줄 | 없음 | 입력에 없음 |
| 200줄 | 200줄 | 없음 | 입력에 없음 |
| 201줄 | 200줄 | 있음 | 전송 안 됨 |

200은 **원문 diff 줄**의 한도다. 헤더·빈 줄도 센다. 여기에 절단 안내, 프롬프트, 재생성 문맥이 붙으므로 전체 HTTP 요청이 200줄인 것은 아니다.

### 설명 원고 · 2분

“안전모드는 기본 OFF이고, 켜면 diff의 앞 200줄을 선택합니다. 201번째 줄부터 보내지 않는다는 뜻이며 비밀번호를 찾아 지우지는 않습니다. 첫 200줄 안의 키는 그대로 들어갈 수 있으므로 호출 전에 전송할 diff를 확인해야 합니다.

구현은 전체 문자열을 줄로 나눈 뒤 앞부분을 고릅니다. 헤더와 빈 줄도 세며, 파일이나 hunk 경계를 보존하지 않습니다. 뒤쪽의 중요한 함수가 빠지면 요약할 근거도 사라집니다. 한 줄이 매우 길 수도 있어 200줄이 일정한 토큰 수나 요금을 뜻하지 않습니다. 절단 안내와 프롬프트까지 붙으므로 HTTP 요청 전체가 200줄로 제한되는 것도 아닙니다.

대안으로 파일별 예산을 나누면 뒤쪽 파일도 포함할 수 있지만 관련 hunk가 잘릴 수 있습니다. 패턴 마스킹도 일부 비밀을 놓칠 수 있습니다. 먼저 줄이려는 위험을 정하고 경계 입력과 실제 요청 body를 비교해야 합니다. 비용 상한을 보려면 요청 횟수뿐 아니라 입력·출력 토큰과 모델 요금도 함께 봐야 합니다.”

## 06. diff에서 프롬프트로

`ai_prompt()`는 종류에 맞는 상수 뒤에 선택한 diff를 붙인다. `git status`는 생성 여부를 판단할 뿐 상태 문자열 자체를 프롬프트에 붙이지 않는다. 별도의 변경 배경 입력이나 테스트 실행 결과도 수집하지 않는다.

```python
if output_type == "pr":
    prompt = PR_PROMPT + diff
if output_type == "commit":
    prompt = COMMIT_PROMPT + diff
return prompt
```

| 입력 요소 | 실제 포함 내용 | 목적 |
| --- | --- | --- |
| 작성 과업 | 한국어 commit 또는 PR | 출력 종류와 언어 지정 |
| 형식 계약 | 제목·길이·선택 본문·세 섹션·불릿 | 검증 가능한 출력 유도 |
| 사실성 지침 | diff 밖 사실·미실행 테스트를 지어내지 말 것 | 추정 억제 |
| 변경 맥락 | 같은 calculator diff | 실제 변경을 요약하는 근거 |

### 설명 원고 · 2분

“프롬프트는 모델에게 보내는 작업 설명입니다. 커밋용·PR용 규칙을 따로 두고 마지막에 실제 diff를 붙입니다. 커밋은 제목이 필수이고 본문을 쓰면 핵심 변경 1~2개 불릿으로 제한합니다. PR에는 Why, What, How to Test가 모두 필요합니다. 프롬프트 상수는 원하는 형식을 요청하고, 검증 함수는 실제 응답이 그 형식을 지켰는지 판단합니다.

모델에게는 diff와 규칙만 주고 별도의 개발 배경이나 테스트 실행 결과는 주지 않습니다. 코드에서 읽히는 효과를 설명할 수는 있지만 실제 이슈나 회의 결정을 알아내지는 못합니다. How to Test도 실행 완료를 주장하기보다 확인 방법을 제안해야 합니다. 더 확실한 배경을 입력받거나 이슈를 연결한다면 그 출처와 신뢰도도 설계해야 합니다.

현재 API에는 user 메시지 하나로 규칙과 diff를 함께 보냅니다. 신뢰할 지시와 외부 입력을 별도 역할로 격리하지 않으므로 diff 안의 지시문을 모델이 따를 가능성도 검토 대상입니다. 사실성 지침을 넣은 것만으로 프롬프트 공격 방어까지 검증했다고 볼 수는 없습니다.”

**예측 질문:** 같은 diff라도 커밋과 PR의 결과 형식이 다른 이유를 프롬프트 두 개에서 찾는다.

## 07. API 요청과 응답

실제 호출은 `requests.post()`로 Codyssey의 chat completions 엔드포인트에 JSON을 보낸다. `API_KEY`는 환경변수에서 읽고 `.env`를 로딩할 수 있다. 인증 헤더는 설명자료에 저장하지 않는다. `truststore`는 운영체제 신뢰 저장소를 HTTPS 검증에 연결한다.

```python
json={
    "model": model,
    "messages": [{"role": "user", "content": diff_after_prompt}],
    "temperature": temperature,
    "max_tokens": max_tokens,
},
timeout=10,
```

응답의 `choices[0]["message"]["content"]`를 꺼내고 `finish_reason`이 `length` 또는 `max_tokens`이면 잘린 응답으로 분류한다. 이 신호가 없는 모든 종류의 누락을 완전하게 탐지하는 것은 아니다. `timeout=10`은 HTTP 라이브러리의 연결·읽기 대기 설정이며 명령 전체가 정확히 10초 안에 끝난다는 보장은 아니다.

| 옵션 | 기본값·해석 | 품질·비용·재현성에 미치는 영향 |
| --- | --- | --- |
| `--model` | 미지정·gemini → `gemini-3.1-flash-lite`, opus → `claude-opus-4-8`; 그 외 전달 | 서로 다른 모델의 능력·지원 파라미터가 다를 수 있음. 이름은 현재 코드 매핑이며 제공 상태 전체를 확인한 목록은 아님 |
| `--temperature` | 0.2, 유한한 실수 | 낮추면 대체로 표현이 집중되고 높이면 선택 다양성이 커짐. 정확성이나 동일 문장 재현은 보장하지 않음 |
| `--max-tokens` | 500, 양의 정수 | 생성 출력 한도. 작으면 섹션이 잘릴 수 있고 크게 설정해도 반드시 모두 사용하는 것은 아님 |

“API 요청에는 주소, 인증, 본문이 필요합니다. API 키는 이용 권한을 확인하고, JSON 본문에는 모델·입력·생성 옵션이 들어갑니다. 반환된 JSON에서 초안 문자열을 꺼낸 뒤 형식을 검사합니다. 네트워크 연결 성공과 올바른 초안 생성은 각각 확인해야 합니다.

temperature는 표현 선택의 다양성에 영향을 줍니다. 낮추면 대체로 표현이 집중되고 높이면 다양한 표현을 시도할 수 있지만, 사실 오류를 막거나 같은 문장을 보장하지는 않습니다. 변경 요약에는 기본 0.2를 쓰며, 설정별 품질 비교 실험을 했다는 뜻은 아닙니다.

## 08. 생성 결과의 형식 검증

**핵심 메시지:** 프롬프트로 요청한 규칙을 코드로 다시 확인한다. 문서 형식이 맞아도 사실이 맞는지는 사람이 확인한다.

`ai_validate()`는 비어 있는 응답·터미널 제어문자를 거부하고, 첫 줄을 제목으로 분리한다. 제목과 본문 사이에는 빈 줄이 필요하다. 길이는 앞뒤 공백을 제거한 제목의 Python `len()` 기준이다. 바이트 수나 화면 폭, 사용자가 한 글자로 느끼는 결합 묶음 수와는 다르다.

| 대상 | 허용 조건 | 실제 경계 결과 |
| --- | --- | --- |
| 커밋 제목 | 표시 내용이 있는 한 줄, 최대 72자 | 72 허용 / 73 거부 |
| 커밋 본문 | 생략 가능, 있으면 내용 있는 `- ` 불릿 1~2줄 | 제목만 있어도 허용 |
| PR 제목 | 표시 내용이 있는 한 줄, 최대 80자 | 80 허용 / 81 거부 |
| PR 본문 | 실제 H2 Why·What·How to Test 각각 1개, 순서 일치, 각 불릿 | 누락·중복·가짜 섹션 거부 |

```python
title_limit = 72 if output_type == "commit" else 80
if len(title) > title_limit:
    raise ValueError(f"제목은 {title_limit}자 이하여야 합니다.")
```

문자열 `## Why`가 있다는 것만 확인하면 코드 블록 속 설명도 섹션으로 잘못 인정한다. `_markdown_structure()`는 `MarkdownIt("commonmark")`의 토큰을 따라 실제 최상위 헤딩과 내용 있는 목록을 찾는다. HTML 주석 속 섹션, 내용 없는 목록, 코드 블록 속 가짜 섹션은 통과하지 않는다. 반대로 실제 테스트 불릿 안의 내용 있는 코드 블록은 허용한다. 표시할 내용이 없는 Unicode 문자만 있는 제목·불릿은 거부하고, 정상 문구와 함께 쓰인 문자는 보존한다.

### 설명 원고 · 4분

“AI가 요청한 규칙을 매번 지킨다고 가정할 수 없어 길이와 구조를 코드로 다시 검사합니다. 커밋 제목은 최대 72자라서 72자는 허용하고 73자는 거부합니다. 본문은 선택이지만 있으면 내용 있는 불릿 1~2줄이어야 합니다. PR은 최대 80자 제목과 Why·What·How to Test 세 섹션을 요구합니다.

문자열 `## Why`가 있다고 실제 섹션인 것은 아닙니다. 코드 블록이나 HTML 주석 속 글자일 수 있습니다. Markdown 파서는 제목·목록·코드를 구분합니다. 현재 검증은 CommonMark 토큰의 level과 source map으로 실제 최상위 H2를 찾고, 이름·순서·중복과 각 섹션의 불릿을 확인합니다. 이름 뒤 괄호 설명은 허용하지만 다른 상위 헤딩 너머의 불릿을 가져와 채울 수는 없습니다.

불릿이 있어도 공백이나 보이지 않는 문자, 빈 HTML뿐이면 내용으로 인정하지 않습니다. 반대로 실제 테스트 불릿 안의 내용 있는 코드 블록은 허용합니다. 제목 길이도 Python `len()` 기준이라 바이트 수·화면 폭·사람이 한 글자로 느끼는 묶음 수와 다를 수 있습니다. 정의가 모호한 부분은 정책과 테스트를 맞추는 것이 중요합니다.

**함께 읽기:** 정상 문서와 코드 블록 속 가짜 세 섹션을 비교한다. 문자열 포함 검사·Markdown 파서·사실 검토가 각각 무엇을 잡는지 하나씩 제시한다.

## 09. 재생성과 오류 종료

**핵심 메시지:** 결과를 고치면 나아질 실패와 설정·연결을 고쳐야 할 실패를 다르게 처리한다.

```text

       → 형식 오류 / 토큰 한도 → 실패 이유를 붙여 요청 2 → 검증 → 출력 또는 종료
       → 인증 / HTTP / 연결 오류 → 바로 종료
```

재요청 프롬프트에는 원래 과업·diff, 실패 사유, 가능한 경우 이전 출력이 들어간다. 토큰 한도 응답은 불완전한 응답으로 처리하므로 이전 출력 문맥을 넣지 않는다. 재요청에서도 model·temperature·max_tokens는 같다. 두 번째 형식 실패는 ValueError, 두 번째 토큰 한도는 RuntimeError로 올라가 CLI가 종료 코드 1로 처리한다.

| 실패·상태 | 처리 | 종료 코드 |
| --- | --- | --- |
| 변경 없음 / 수집할 diff 없음 | 생성 생략 | 0 |
| 잘못된 CLI 옵션 | argparse가 요청 전 거부 | 2 |
| 키 누락·401/403·429·서버·TLS·연결·타임아웃 | 원인 안내, 자동 재요청 없음 | 1 |

### 재생성 선택 이유 · 평가질문 #15

### 설명 원고 · 2분

“첫 응답의 형식이 틀리거나 토큰 한도로 잘리면 실패 이유를 붙여 한 번 더 요청합니다. 두 번째도 실패하면 멈춥니다. 형식 오류인 ValueError와 불완전 응답인 IncompleteResponseError가 이 경로에 해당합니다. 키 누락·HTTP·연결 오류는 글을 다시 써서 해결되지 않으므로 바로 원인을 안내합니다. 응답 JSON 자체가 잘못된 경우도 RuntimeError로 종료합니다.

## 사후 학습용 용어와 코드 안내

| 용어 | 이 프로젝트에서의 뜻 |
| --- | --- |
| CLI·진입점 | 터미널 인자를 받아 main으로 연결하는 `output-6-1` |
| subprocess | 별도 Git 프로세스를 실행하고 stdout·오류·종료 코드를 받는 방법 |
| 작업 트리·인덱스·HEAD | 편집 중 파일·다음 커밋 후보·현재 커밋 기준 |
| diff·hunk | 두 상태의 차이·차이를 문맥 줄과 함께 보여주는 묶음 |
| 프롬프트 | 모델에게 보내는 작성 규칙과 변경 맥락 |
| JSON·직렬화 | 모델·messages·옵션을 HTTP 본문의 구조화된 텍스트로 표현 |
| 인증·TLS | API 이용 권한 확인·통신 상대와 전송 보호를 위한 HTTPS 검증 |
| 토큰·temperature | 모델의 텍스트 처리 단위·생성 선택 다양성에 영향을 주는 설정 |
| 파서·구문·의미 | 문서 구조를 읽는 도구·형식 규칙·내용이 사실과 맞는지의 문제 |
| 모의 응답 | 외부 서비스 대신 제어한 응답을 넣어 경계 동작을 검사하는 방법 |
| 재생성·후처리 | API에 다시 작성 요청·이미 생성된 문자열을 로컬에서 정리 |

코드 읽기는 `main.py:generate_commit()` → `git_service.py:run_git()` → `ai_service.py:ai_commit()` → `_prepare_diff()` → `ai_prompt()` → `ai_generate_validated()` → `ai_call_api()` → `ai_validate()` 순서로 진행한다. PR은 같은 경로에서 템플릿과 검증 종류가 바뀐다. 숫자 줄 위치는 기준 SHA에서의 안내이며 파일 변경 뒤에는 함수명을 기준으로 찾는다.

## 발표 준비와 확인 경계

PPT는 별도 표지 없이 12장이며 텍스트·표·흐름도는 편집 가능하다. 실행 로그 이미지만 래스터로 삽입했다. 이미지의 원문과 실행 조건은 실행기록에 남겼다. 발표자 노트는 이 문서의 대응 장과 근거를 가리킨다.

실제 PowerPoint 앱에서 열어 본 여부, 렌더링·파일 검수 결과와 리허설 상태는 [실행기록의 제작 검수](근거/실행기록.md#제작-검수)에 기록한다. 예상 시간표를 실측 리허설로 주장하지 않는다. 사용자 발표 전에는 글꼴과 화면 배율을 확인하고 설명 원고로 한 번 읽어 시간을 조정한다.
