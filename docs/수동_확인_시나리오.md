# 수동 확인 시나리오

이 문서는 과제요구서의 기능 요구사항과 제한사항을 사람이 직접 실행하고 판정하는 안내서입니다. 실행 대상은 output_6_1입니다. 요구사항과 구현 정책의 차이를 먼저 읽고, 각 시나리오의 준비·명령·기대 결과·증거·복구 절차를 따릅니다.

## 1. 기준 자료와 판정 원칙

- 과제 원문: AI 기반 Git 커밋 & PR 자동 생성기 개발.pdf
- 요구사항 정리: AI기반_Git커밋_PR자동생성기_개발.md 및 SRS.md
- 평가 질문: 평가질문.md. 16개 문장은 평가 근거에서 복원한 질문이며 원문 평가지를 그대로 옮긴 문장이 아닙니다.
- 실행 기준: README.md, pyproject.toml, src/output_6_1/
- 이번 실제 실행 기록: [실행 결과](manual_check/실행결과_2026-10-19.md)

과제 필수 요구사항, 권장사항, 선택 과제, 현재 구현 정책을 구분합니다. 원문이 정하지 않은 Git 변경 범위나 글자 수 계산을 과제의 고정 기준으로 확대하지 않습니다.

실제 API 결과와 관찰 도구의 모의 HTTP 응답을 구별합니다. 모의 실행은 요청 내용·옵션 전달·오류·재시도를 확인하며 실제 API 성공을 입증하지 않습니다. 모델 생성 문구가 매번 같을 것을 요구하지 않습니다.

## 2. 확인된 현재 구현 정책

| 항목 | 과제 기준 | 현재 구현에 맞춰 확인할 내용 |
| --- | --- | --- |
| 실행 환경 | Python 3.10 이상, 터미널 CLI | 프로젝트는 Python 3.12 이상을 요구한다. 3.10 지원을 임의로 합격 조건에 넣지 않는다. |
| 진입점 | 구체적인 실행 파일명은 예시 | `uv run --locked output-6-1` 또는 설치된 Python의 `-m output_6_1.main` |
| 변경 수집 | `git status`, `git diff` | `git status --short`와 기본 `git diff`. 생성 대상은 추적 파일의 unstaged 변경이다. |
| 키 | 환경변수, 하드코딩 금지 | 환경변수 이름은 `API_KEY`. `.env`도 읽으므로 키 누락 실험에 영향을 준다. |
| 기본 설정 | 모델·temperature·max_tokens 기본값 및 CLI 변경 | 코드 기준 기본 모델 `gemini-3.1-flash-lite`, temperature `0.2`, max_tokens `500` |
| 모델 별칭 | 별칭 자체는 필수 아님 | `gemini`는 기본 모델명, `opus`는 `claude-opus-4-8`로 변환한다. 다른 이름은 그대로 전달한다. |
| Opus 설정 | 과제에 모델별 예외 규정 없음 | `opus`와 `claude-opus-*`에는 temperature를 전송하지 않는다. 재시도에서도 동일하다. |
| 안전모드 | 마스킹 또는 전송량 제한 중 하나 이상 필수 | 기본 OFF. ON이면 diff 원문 앞 200줄을 보낸다. 초과 시 잘림 표식을 추가한다. 마스킹 기능은 없다. |
| 제목·본문 | 커밋 72자, PR 80자, PR 세 섹션·불릿 | 제목은 앞뒤 공백 제거 후 Python `len()` 기준. 현재 커밋 본문은 선택이며, 있으면 1~2개 불릿을 요구한다. |
| 재생성 | 재생성 또는 후처리 중 하나 | 형식 오류·토큰 잘림만 1회 재생성. 명령당 API 요청은 최대 2회다. |
| 오류 | 원인을 포함한 안내 | 처리된 실행 오류 `1`, 옵션 오류 `2`, 정상·생성 생략 `0` |

모델명은 현재 코드의 전달값을 설명한다. 해당 모델의 실제 제공 여부나 계정 접근 권한이 확인되었다는 뜻은 아니다.


관찰기 모의 응답으로 요청과 오류 경계를 확인합니다. 실제 API 정상 흐름은 M06·M07에서 각 한 번 실행하며, 추가 모델·temperature 비교는 필요할 때만 선택합니다.

## 3. 시작 준비와 명령 실행

### 3.1. clone·설치·환경 기록

새 작업 위치에 저장소를 clone하고 README 설치 절차를 따릅니다.

~~~console
git clone https://github.com/kjs83036/AI-SW-Basic-B6-2.git output_6_1
cd output_6_1
git rev-parse HEAD
uv sync --locked --system-certs
uv run --locked output-6-1 --help
uv run --locked output-6-1 commit --help
uv run --locked output-6-1 pr --help
~~~

Python 3.12 이상을 사용하고, README의 OS별 전용 가상환경 경로를 설정합니다. Python 버전·OS·셸·제품 SHA를 결과 양식에 적습니다. README만으로 설치와 도움말 확인이 되는지 기록합니다.

### 3.2. 실제 API Key

실제 호출은 README가 안내하는 API_KEY 환경변수 또는 저장소 루트의 .env를 사용합니다. 키 값은 출력·명령 기록·화면 캡처에 남기지 않습니다. 실제 호출은 M06·M07에서 각각 수행합니다. 키 누락은 모의 사례로 재현합니다.

### 3.3. 독립 실험 Git 저장소

제품 파일을 건드리지 않도록 임시 경로에 실험 저장소를 만듭니다. 아래 예시는 macOS zsh입니다. PowerShell용 파일 생성 명령은 M04와 안전모드 사례를 따릅니다.

~~~console
mkdir -p "$TMPDIR/output-6-1-manual/basic"
cd "$TMPDIR/output-6-1-manual/basic"
git init
git config user.name "수동 확인"
git config user.email "manual@example.invalid"
git config commit.gpgsign false
git config core.autocrlf false
python -c 'from pathlib import Path; Path("greeting.py").write_text("def greet(name):\n    return f\"Hello, {name}\"\n", encoding="utf-8")'
git add greeting.py
git commit -m "검증용 기준 상태"
python -c 'from pathlib import Path; Path("greeting.py").write_text("def greet(name):\n    return f\"안녕하세요, {name}님\"\n", encoding="utf-8")'
git status --short
git diff
~~~

추적 파일을 먼저 기준 커밋에 넣고, 그 뒤 unstaged 수정을 만듭니다. 새 파일만 있으면 현재 diff 수집 경로에 포함되지 않습니다. 사례마다 별도 폴더를 만들거나 시작 상태를 다시 준비합니다.

### 3.4. 안전한 HTTP 관찰기

관찰 도구는 docs/manual_check/observe_cli.py에 있습니다. 실제 제품 main 진입점을 실행하면서 요청 직전의 requests.post를 모의 응답으로 바꿉니다. 요청 JSON·응답·횟수를 보여주고 Authorization 헤더는 출력하지 않습니다. 실제 네트워크 요청은 발생하지 않습니다.

제품 저장소 루트에서 임시 저장소를 대상으로 실행합니다.

~~~console
uv run --locked python docs/manual_check/observe_cli.py --mode inspect --project . --git-dir "$TMPDIR/output-6-1-manual/basic" -- commit
~~~

commit을 pr로 바꾸거나 제품 옵션을 -- 뒤에 추가합니다. 고정 오류 응답은 다음처럼 지정합니다.

~~~console
uv run --locked python docs/manual_check/observe_cli.py --mode fixture --case http-401 --project . --git-dir "$TMPDIR/output-6-1-manual/basic" -- pr
~~~

관찰 도구는 diff의 민감정보를 가리지 않습니다. 합성된 가짜 데이터만 사용합니다. 사례 목록은 M09~M24 및 E03~E15에 연결되어 있습니다.

## 4. 설치와 추적 파일 준비 시나리오

### M01. Git clone부터 CLI 도움말까지

대응: FR-62-06, AC-62-10, 개발 환경 조건.

1. Git·uv·사용할 Python 버전을 확인하고 기록한다.
2. 새 `workspace/`에서 원격 저장소를 `checkout`으로 clone한다.
3. `checkout`으로 이동해 README와 잠금 파일을 확인한다.
4. README의 운영체제별 전용 가상환경 설정을 적용한다. 동기화 폴더 사이에 가상환경을 공유하지 않는다.
5. `uv sync --locked --system-certs`를 실행한다. Python 3.12가 없으면 README에 적힌 설치 절차를 선행한다.
6. 전체 도움말과 `commit --help`, `pr --help`를 확인한다.
7. `uv run --locked python -c "import sys; print(sys.executable)"`로 설치된 Python 위치를 확보해 이후 `tool_python`으로 사용한다.
8. clone한 SHA와 검증할 로컬 SHA를 대조한다. 미게시 로컬 변경이 있으면 서로 다른 검증 대상으로 기록한다.

저장소를 clone하는 명령은 다음과 같습니다. 주소를 안다는 사실만으로 clone 성공이나 원격 최신 SHA를 확인한 것으로 보지 않습니다.

```console
git clone https://github.com/kjs83036/AI-SW-Basic-B6-2.git checkout
cd checkout
git rev-parse HEAD
uv sync --locked --system-certs
uv run --locked output-6-1 --help
uv run --locked output-6-1 commit --help
uv run --locked output-6-1 pr --help
uv run --locked python -c "import sys; print(sys.executable)"
```

통과: README 절차만으로 설치·실행 가능하고 네 명령과 생성 옵션을 찾을 수 있다. 안내서에만 있는 추가 설치 요령이 필요했다면 README 재현성 문제로 기록한다.

### M02. 키 설정과 기본 상태 확인

대응: FR-62-02·06.

- 실제 키는 셸 환경변수 `API_KEY`에 설정한다. 입력 방법은 zsh의 숨김 입력 또는 PowerShell 보안 입력을 사용해 화면과 셸 이력에 키를 남기지 않는 방법을 안내한다.
- 값 자체를 출력하지 않고 설정 여부만 확인한다.
- `.env` 사용은 README 호환성 확인으로 분리한다. 환경변수 직접 설정으로 동작하는지도 반드시 확인한다.
- 키 설정 자체로 API를 호출하지 않는다. M06·M07에서 실제 생성으로 연결한다.
- 모의 실행은 별도 프로세스에서 가짜 키를 사용하고 기존 셸 키를 덮어쓰지 않는다.

### M03. 변경 없음

대응: FR-62-01, AC-62-02.

새 실험 저장소에 기준 커밋을 만든 뒤 파일을 수정하지 않는다. `status`, `diff`, `commit`, `pr`을 차례로 실행한다.

통과: 상태·diff가 비어 있음을 안내하며 생성 결과는 없고 종료 코드는 `0`이다. 관찰기에서 생성 명령의 실제 요청 수가 `0`인지 확인한다. 관찰기·결과 로그를 실험 저장소 밖에 두어 로그 파일이 미추적 변경으로 잡히지 않게 한다.

### M04. 파일을 추적시킨 뒤 수정

대응: FR-62-01·03·04, AC-62-01.

임시 cases/basic 저장소에서 아래 순서를 실행합니다. 검사자가 만드는 기준 커밋이 변경 비교의 기준점입니다.

```console
git init
git config user.name "수동 확인"
git config user.email "manual@example.invalid"
git config commit.gpgsign false
git config core.autocrlf false
python -c 'from pathlib import Path; Path("greeting.py").write_text("def greet(name):\n    return f\"Hello, {name}\"\n", encoding="utf-8")'
git add greeting.py
git commit -m "검증용 인사 함수 기준 상태 추가"
python -c 'from pathlib import Path; Path("greeting.py").write_text("def greet(name):\n    return f\"안녕하세요, {name}님\"\n", encoding="utf-8")'
git status --short
git diff
```


위 명령은 macOS zsh용입니다. Windows PowerShell에서는 다음 블록으로 같은 추적 파일과 unstaged 변경을 준비합니다.
~~~powershell
$caseDir = Join-Path $env:TEMP "output-6-1-manual\basic"
New-Item -ItemType Directory -Force -Path $caseDir | Out-Null
Set-Location $caseDir
git init
git config user.name "수동 확인"
git config user.email "manual@example.invalid"
git config commit.gpgsign false
git config core.autocrlf false
@'
def greet(name):
    return f"Hello, {name}"
'@ | Set-Content -Path greeting.py -Encoding utf8
git add greeting.py
git commit -m "검증용 인사 함수 기준 상태"
@'
def greet(name):
    return f"안녕하세요, {name}님"
'@ | Set-Content -Path greeting.py -Encoding utf8
git status --short
git diff
~~~


통과: `greeting.py`가 `??`가 아닌 unstaged 수정 상태로 보이고 diff에 영어 인사 삭제·한국어 인사 추가가 나온다. 변경 후에는 다시 `git add`하지 않는다.

### M05. `status`, `diff`를 원래 Git 출력과 비교

대응: FR-62-01, 수집 범위 제약.

- M04 상태에서 제품 `status`를 실행하고 `git status --short`와 파일·상태를 비교한다.
- 제품 `diff`를 실행하고 `git diff`와 경로·삭제·추가 내용을 비교한다.
- 두 명령 모두 AI 호출 수 `0`, 종료 코드 `0`을 확인한다.
- 상태의 첫 두 열은 공백도 의미가 있으므로 ` M`, `M `, `MM`, `??`를 지우지 않은 예시를 제공한다.

### M06. 실제 API로 커밋 메시지 생성

대응: FR-62-02·03·07, AC-62-01·05.

M04의 동일한 unstaged 변경에서 `"$tool_python" -m output_6_1.main commit`을 실행한다.

통과: 실제 요청이 성공하고 `-- Commit Message --` 구획과 한 줄 제목이 나온다. 제목은 72자 이하이며 50자 이하는 권장 준수로 따로 기록한다. 본문이 있다면 과제의 최소 기준을 확인하고 현재 구현의 1~2개 불릿 정책도 확인한다. 내용이 실제 인사 문구 변경을 설명하며 수행하지 않은 테스트를 완료했다고 단정하지 않는지 사람이 읽는다.

생성 문구만 복사해 저장소 밖 텍스트 편집기에 붙여넣는다. 도구가 실제 커밋을 만들었는지는 M25에서 별도로 확인한다.

### M07. 실제 API로 PR 제목·본문 생성

대응: FR-62-02·04·07, AC-62-01·05.

동일한 변경에서 `"$tool_python" -m output_6_1.main pr`을 실행한다.

통과: 실제 API 성공, PR 제목 한 줄·80자 이하, 제목/본문 구획, `Why`·`What`·`How to Test` 헤더와 각 섹션의 내용 있는 불릿을 확인한다. 괄호 안 한국어 설명 유무는 실패 조건이 아니다. 초안의 사실관계·제안한 테스트와 실제 실행 사실을 구분해서 읽는다.

### M08. Git 상태별 생성 대상 확인

대응: FR-62-01, AC-62-11. 원문이 고정하지 않은 구현 정책 확인이다.

각 행은 독립 실험 저장소에서 수행하거나 직전 상태를 명시적으로 복구한 뒤 수행한다. `commit`과 `pr` 양쪽을 모의 응답으로 확인한다.

| 상태 | 만드는 방법 | 기대 결과 |
| --- | --- | --- |
| unstaged만 있음 | 기준 커밋 뒤 추적 파일 수정 | status·diff 모두 변경 표시, 생성 요청 있음 |
| staged만 있음 | 수정 후 `git add greeting.py` | status에 변경, 기본 diff는 없음, 수집할 diff 없음 안내, 요청 0회 |
| untracked만 있음 | 깨끗한 저장소에 `notes.txt` 새로 생성 | status에 `??`, 기본 diff 없음, 생성 생략·요청 0회 |
| 같은 파일에 staged와 unstaged | 1차 수정→add→2차 수정 | status에 `MM`, 요청에는 2차 수정의 unstaged diff만 포함 |
| 추적 파일 삭제 | 기준 커밋 뒤 실험 파일만 삭제 | status·diff에 삭제가 나타나며 삭제 내용을 기반으로 생성 |
| 바이너리 변경 | NUL을 포함한 파일을 기준 커밋한 뒤 바이트 수정 | Git의 바이너리 변경 안내만 수집. 원시 바이트를 읽었다고 기록하지 않음 |

혼합 상태에서는 `git diff --cached`도 검사자가 확인용으로 실행해 staged 내용이 요청에서 제외되었는지 비교한다. 검사자가 쓰는 확인 명령과 제품이 변경 수집에 사용하는 명령을 구분한다.

## 6. 모델·temperature·max_tokens 변경

### M12. 기본값과 모델 변경

대응: FR-62-02, AC-62-04.

M04의 작은 동일 diff를 사용한다. 먼저 inspect 모드로 양쪽 생성 명령의 요청을 비교하고, 실제 접근 가능한 모델을 확인한 뒤 대체 모델 1개로 실API 실행을 수행한다.

| CLI 옵션 | 요청에서 확인할 값 |
| --- | --- |
| 옵션 생략 | `model=gemini-3.1-flash-lite`, `temperature=0.2`, `max_tokens=500` |
| `--model gemini` | 기본 모델 정식 이름으로 변환 |

| `--model manual-test-model` | 모의 실행에서 이름 그대로 전달 |

실API에서는 코드에 적힌 이름이 실제로 제공되는지 별도로 확인한다. 접근 권한이 없거나 모델을 제공하지 않으면 서비스 조건으로 기록한다. 임의의 모델명 전달과 실제 다른 모델 생성 성공은 별개의 결과이다.

### M13. temperature 변경

대응: FR-62-02, 과제 목표의 파라미터 영향 설명.

```console
"$tool_python" -m output_6_1.main commit --model gemini --temperature 0.1 --max-tokens 500
"$tool_python" -m output_6_1.main commit --model gemini --temperature 0.8 --max-tokens 500
```

- 양쪽 명령의 옵션만 바꾸고 diff·모델·토큰은 고정한다.
- inspect 모드에서 요청 값 `0.1`, `0.8`을 직접 확인한다. `pr`에도 동일 옵션이 적용되는지 확인한다.
- 실제 API가 값을 허용할 때 결과의 표현 차이를 읽고 기록한다. 출력이 반드시 달라져야 합격이라는 조건은 두지 않는다.
- `opus --temperature 0.8`은 CLI가 값을 받아도 요청 JSON에는 temperature가 없음을 확인한다. 재시도에도 없어야 한다.
- 현재 CLI는 유한한 실수만 검사하며 모든 모델 공통의 `0~1` 또는 `0~2` 범위를 구현하지 않는다. 서비스의 범위 제한을 제품의 로컬 검증 규칙으로 혼동하지 않는다.

### M14. max_tokens 변경과 출력 잘림

대응: FR-62-02·07.

- 같은 diff에서 `--max-tokens 128`, `--max-tokens 800`을 비교하고 요청 JSON의 값이 바뀌는지 본다. `commit`과 `pr` 모두 확인한다.
- max_tokens는 출력 토큰 상한이며 제목 글자 수나 diff 입력 줄 수가 아니다. 상한을 늘려도 응답이 반드시 길어지지는 않는다.
- 작은 토큰 값의 실제 응답은 관찰용으로만 사용한다. 잘림 재현은 모의 응답의 `finish_reason=length` 또는 `max_tokens`로 확정한다.
- 첫 잘림→정상 응답: 요청 2회, 최종 정상 결과만 출력, 종료 코드 `0`.
- 두 번 잘림: 요청 2회 후 오류·종료 코드 `1`. 세 번째 요청 없음.
- 재시도에서도 사용자가 준 model·temperature 정책·max_tokens가 유지되는지 비교한다.

### M15. 잘못된 옵션과 알 수 없는 명령

대응: CLI 설정 정책 확인. 원문의 별도 숫자 범위 요구로 분류하지 않는다.

| 입력 | 기대 결과 |
| --- | --- |
| `--temperature=nan`, `--temperature=inf`, `--temperature=-inf` | 유한한 실수 안내, 종료 코드 2, 요청 0회 |
| `--temperature abc` | 숫자 오류 안내, 종료 코드 2, 요청 0회 |
| `--max-tokens 0`, `--max-tokens=-1`, `--max-tokens 1.5` | 양의 정수 안내, 종료 코드 2, 요청 0회 |
| 알 수 없는 하위 명령 또는 옵션 | 사용법 안내, 종료 코드 2, 요청 0회 |

`opus` 모델에서도 잘못된 temperature 입력은 CLI 단계에서 거절하는지 확인한다.

## 7. 환경·API 오류 시나리오

M16~M21은 유효한 unstaged diff를 먼저 준비한다. 변경이 없으면 API 경로 전에 종료하므로 원하는 오류를 재현할 수 없다.

### M16. API_KEY 누락

대응: FR-62-02, AC-62-03.

실제 누락 상태는 API_KEY와 .env가 모두 없는 환경에서 재현합니다. 관찰기의 missing-key fixture는 API_KEY를 제거하고 PYTHON_DOTENV_DISABLED=1로 .env 읽기도 끕니다. 이는 관찰기 전용 설정이지 제품 CLI 옵션이 아닙니다.

통과: `API_KEY` 미설정 원인이 표시되고 종료 코드 `1`, 실제 HTTP 요청 `0`회이다. 검증 후 검사자의 원래 키·`.env`는 보존되어야 한다.

### M17. 인증·권한 오류

대응: FR-62-02, AC-62-03.

모의 HTTP 401·403을 각각 반환한다. 서버 메시지는 가짜 키 문자열을 포함한 버전도 사용한다.

통과: 인증·권한 확인 안내, 종료 코드 `1`, 요청 1회이며 형식 재시도를 하지 않는다. 오류 출력에서 키가 노출되지 않는지 확인한다. 모의 결과를 실제 인증 실패 관찰로 기록하지 않는다. 실제 잘못된 키 실험은 필요할 때 별도 실행하고 요청 비용·계정 조건을 기록한다.

### M18. 연결 실패와 요청 시간 초과

대응: FR-62-02, AC-62-03.

- 모의 `ConnectionError`와 `Timeout`을 각각 발생시켜 원인이 구분되는지 본다.
- 통과: 각각 연결 불가·시간 초과 안내, 종료 코드 `1`, 요청 시도 1회, 성공 초안 없음.
- 실제 네트워크 단절 확인이 필요하면 검사자가 연결을 끊고 실행한 뒤 복구한다. 이때 DNS 실패와 시간 초과 중 어느 결과가 나올지 고정하지 않는다. 관찰한 원인만 기록한다.

### M19. 기타 서비스·응답 오류

대응: 오류 처리 보완 확인.

모의 HTTP 429, 500, 잘못된 JSON, `choices` 누락, 비문자열 content를 각각 반환한다. TLS 오류도 모의로 별도 확인한다.

통과: 요청 한도·서버 오류·응답 형식·인증서 문제를 적절하게 안내하고 정상 생성처럼 끝나지 않는다. 종료 코드 `1`을 기록한다. 429 재현을 위해 실제 API를 반복 호출하지 않는다.

### M20. Git 저장소 밖 실행

대응: 실행 전제와 Git 오류 처리.

새로운 일반 디렉터리에서 설치된 Python으로 `status`, `diff`, `commit`, `pr`을 실행한다. 상위 경로에도 `.git`이 없는 위치를 선택한다.

통과: Git 저장소 관련 오류와 종료 코드 `1`, API 요청 `0`회이다. 도구 설치 프로젝트를 현재 디렉터리로 잘못 잡아 정상 실행시키지 않도록 위치를 표시한다.

### M21. 오류 출력의 비밀값·제어문자

대응: 구현의 안전한 오류 표시 보완.

관찰기에서 `http-control` fixture를 선택해 가짜 키·ESC·NUL이 포함된 HTTP 오류를 재현한다.

~~~console
uv run --locked python docs/manual_check/observe_cli.py --mode fixture --case http-control --project . --git-dir "$TMPDIR/output-6-1-manual/basic" -- commit
~~~

통과: 키는 `[REDACTED]`로 가려지고 ESC·NUL은 `\x1b`, `\x00`처럼 실행되지 않는 문자열로 표시된다. 제품의 오류 메시지 마스킹과 diff 안전모드 마스킹은 다른 기능으로 설명한다.

## 8. 출력 길이·형식 검증과 재생성

대응: FR-62-03·04·07, AC-62-05·06.

실제 모델에게 일부러 규칙을 어기라고 요청하는 방식은 사용하지 않는다. 모의 HTTP 응답으로 잘못된 결과를 정확하게 넣고, 제품 CLI의 실제 검증·재생성 경로를 확인한다.

~~~console
python -c 'value = input("제목을 붙여 넣으세요: "); print(len(value.strip()))'
~~~

### M25. 초안 생성 전후 저장소 보존

대응: FR-62-05·07, AC-62-08.

각 생성 명령 전후 검사자가 다음을 저장소 밖 증거 디렉터리에 저장해 비교한다.

### M26. 자동 push·GitHub PR 생성 미구현

대응: FR-62-05, Git 연동 범위 제약.

동적 증거와 소스 검토를 함께 사용한다.

- M25의 실행 전후 Git 상태 비교와 관찰한 API 요청을 증거로 연결한다.
- 실제 원격 저장소를 확인할 경우 실행 전후 원격 브랜치 SHA·PR 목록도 읽기 전용으로 비교한다. 검사자가 실행한 조회 명령은 제품의 자동 반영 기능으로 취급하지 않는다.

## 11. 결과 기록과 실행 운영

### 11.1. 결과기록 양식

| 필드 | 기록 내용 |
| --- | --- |
| 시나리오·세부 사례 ID | 예: M09-commit-on, M22-commit-73 |
| 요구사항 구분 | 필수·권장·선택·구현 정책·보완 확인 |
| 환경 | 실행 일시, OS·셸, Python·의존성, 검증 대상 SHA·로컬 변경 유무 |
| 실행 조건 | 시작 디렉터리, 파일 상태, 옵션, 실제 API/모의 응답 |
| 기대 결과 | 출력·요청·종료 코드·상태 |
| 실제 결과 | 관찰 내용, stdout·stderr·요청 증거 위치 |
| API 정보 | 서비스/모델, 요청 건수, 실API 성공 여부. 키는 제외 |
| 판정 | PASS·FAIL·NOT_RUN·BLOCKED·N/A |
| 사유·복구 | 차이점, 미실행 이유, 복구 완료 여부 |

- PASS는 실제로 수행하고 기준을 만족한 경우만 사용한다.
- NOT_RUN은 실행하지 않은 항목, BLOCKED는 키·접근 권한·네트워크 등으로 수행할 수 없었던 항목이다.
- 선택 기능 미구현은 N/A 또는 미수행 사유로 기록하며 필수 기능 실패로 합산하지 않는다.
- 모의 정상 응답 성공을 실API 연동 PASS로 대체하지 않는다.
- 프로그램 오류를 기록하기 전에 생성 입력·실행 위치·가상환경이 맞는지 확인한다.

### 11.2. 증거 보관

세부 사례별로 stdout·stderr·종료 코드와 필요한 요청 JSON·Git 전후 상태만 남긴다. 증거를 저장소 안으로 리다이렉트해 새로운 변경을 만들지 않는다.

zsh는 명령 직후 `$?`, PowerShell은 외부 프로그램 실행 직후 `$LASTEXITCODE`를 변수에 저장한다. 다른 명령을 실행한 뒤 값을 읽거나 파이프의 마지막 명령 코드로 제품 종료 코드를 오판하지 않는다.

증거는 기본적으로 텍스트를 사용한다. 화면 캡처는 필요할 때만 남긴다. 실API 응답에 실험하지 않은 테스트 성공 문구가 있으면 형식 PASS와 사실관계 문제를 별도 기록한다.

### 11.3. 실행 순서와 API 예산

1. M01~M05: 설치·키·Git 입력 준비.
2. M06·M07: 실제 API로 commit/pr 정상 흐름 확인.
3. M08~M15: 모의 요청 관찰 중심으로 입력 범위·안전모드·설정 확인. 실제 대체 모델·파라미터 비교는 필요한 사례만 실행.
4. M16~M24: 제어된 오류·형식·재생성 확인.
5. M25~M28: 상태 보존·문서·제출 확인.
6. M29·M30: 선택 과제와 학습 목표를 분리 확인.

실API 최소 필수 경로는 commit/pr 두 명령이며 형식 재생성이 발생하면 현재 정책상 합계 최대 4회이다. 대체 모델 1회·temperature 두 값·토큰 두 값의 실제 비교를 추가하면 5개 명령, 최대 10회 요청이 더 발생할 수 있다. 모의 실행은 유료 AI API 요청을 발생시키지 않는다. 실제 비용은 서비스 정책에 따라 다르므로 고정 금액을 적지 않는다.

### 11.4. 복구 원칙

- 실험은 전용 저장소에서만 한다. 기존 작업 트리·기존 설명자료를 초기화하지 않는다.
- `git reset --hard`, `git clean -fd`, 광범위 삭제를 기본 안내에 넣지 않는다.
- 특정 실험 파일의 unstaged 변경은 해당 실험 저장소에서 `git restore --worktree <파일>`로만 되돌린다. staged 복구는 해당 경로에 `git restore --staged <파일>`을 먼저 적용한다.
- untracked 실험 파일과 증거 폴더는 검사자가 경로와 내용을 확인한 뒤 정리하거나 그대로 보관한다.
- 네트워크 단절 실험 후 연결을 복구하고 임시 환경변수는 실행 전 값으로 되돌린다. 키는 가능하면 자식 프로세스에서만 변경해 복구 필요를 줄인다.

## 12. 평가 질문별 시나리오 16개

### E12. temperature 영향과 재현성 설명

평가 질문 12. README의 생성 파라미터와 응답 처리 근거를 읽고, 같은 모델·diff·max_tokens에서 temperature 0.1과 0.8을 inspect로 비교합니다. 옵션이 요청에 반영되는지 확인합니다. 실제 API 권한이 있으면 각 설정을 한 번 실행해 차이를 관찰하되 한 쌍의 출력으로 통계적 결론을 내리지 않습니다. 높은 값은 다음 토큰 선택의 다양성을 키우는 경향, 낮은 값은 상대적 일관성을 돕는 경향이 있지만 모델·입력마다 영향이 다르고 같은 설정만으로 문장이 보장되지 않는다고 설명합니다.

### E15. 재생성과 후처리의 선택 이유

평가 질문 15.
